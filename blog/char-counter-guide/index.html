글자수와 바이트: 제출 화면과 결과가 다를 때

최초 작성 2026-05-02 · 수정 2026-10-25

문서가 “700자 이내”라고 해서 어느 도구에서나 같은 숫자가 나오는 것은 아닙니다. 공백 포함 여부뿐 아니라 줄바꿈, 이모지, 문자 인코딩 처리도 다를 수 있습니다. 제한의 최종 기준은 제출처의 실제 입력 화면과 공고입니다.

검증할 수 있는 세 가지 입력 예시

입력공백 포함공백 제외UTF-8 바이트
안녕 하세요6516
ABC 123767
가 + 줄바꿈 + 나327

첫 번째 예시는 한글 다섯 글자와 공백 한 칸입니다. UTF-8에서 이 예시의 한글 음절은 각각 3바이트이고 공백은 1바이트이므로 5 × 3 + 1 = 16바이트입니다. 표의 세 번째 입력은 “가” 다음에 엔터를 한 번 누르고 “나”를 입력한 경우입니다. 다른 프로그램에서 줄바꿈을 CRLF 두 코드로 저장하면 파일의 바이트 수가 달라질 수 있습니다.

화면에 한 글자로 보여도 길이는 다를 수 있습니다

JWAY의 기본 글자수는 JavaScript 문자열의 UTF-16 코드 단위 길이입니다. 일반적인 한글 음절과 영문은 1씩 계산되지만, U+1F600 같은 이모지는 2로 계산됩니다. 여러 이모지와 결합 문자가 합쳐져 한 그림으로 보이는 경우도 있습니다. 화면에서 보이는 덩어리 수, 유니코드 코드 포인트 수, UTF-16 길이는 서로 다른 기준입니다.

이는 특정 채용 시스템이나 SNS가 같은 방법을 사용한다는 뜻이 아닙니다. 이모지가 포함된 문서라면 제출 화면에서 차이가 나는 부분을 별도로 확인하세요. 근거: MDN String.length.

바이트 제한이라면 인코딩부터 확인

UTF-8 바이트는 실제 UTF-8 인코딩 길이를 계산합니다. “한글 2바이트 추정”은 한글을 2, ASCII 문자·공백을 1로 가정한 단순 비교값입니다. 실제 EUC-KR 인코더가 아니며 모든 한글의 표현 가능 여부를 검증하지 않습니다. 이모지·한자 등 추정 범위 밖 문자가 있으면 계산 불가로 표시합니다.

EUC-KR, CP949, UTF-8을 같은 것으로 보지 마세요. 제출처가 인코딩을 명시하지 않았다면 추정값이 낮다는 이유로 제출 가능하다고 판단할 수 없습니다. MDN TextEncoder 문서는 UTF-8 인코딩의 기본 동작을 설명합니다.

자기소개서를 줄이는 작업 순서

  1. 문항이 요구한 경험·역할·결과가 들어 있는지 먼저 확인합니다.
  2. 공고에 적힌 제한과 공백 기준을 그대로 기록합니다.
  3. 중복된 수식어와 같은 내용을 반복한 문장을 줄입니다.
  4. 문장을 고친 뒤 글자수와 내용의 의미를 함께 다시 확인합니다.
  5. 최종 제출 화면에 붙여넣고 줄바꿈과 제한 경고를 확인합니다.

목표를 무조건 제한의 90~95%로 맞출 필요는 없습니다. 분량을 채우기 위해 경험이나 성과를 꾸며 쓰지 마세요. 요구 사항을 빠뜨리지 않고 제한 안에서 명확하게 전달하는 것이 목적입니다.

플랫폼별 고정 표를 없앤 이유

같은 기업이라도 채용 공고와 문항에 따라 제한이 다릅니다. SNS 역시 기능·요금제·게시물 종류에 따라 제한이나 링크 계산 방식이 달라질 수 있습니다. 이전 글의 회사별 고정 글자수와 일률적인 검색 노출 길이 권장은 삭제했습니다. 현재 제출할 화면의 도움말이 가장 직접적인 기준입니다.

이 도구는 입력 본문을 계산 요청으로 외부에 보내지 않습니다. 다만 사이트의 글꼴·광고 검증 등 외부 리소스 요청은 별도이며, 민감한 문서의 공유 기기 사용에는 주의하세요.
